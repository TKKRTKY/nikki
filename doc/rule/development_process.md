# 開発プロセスルール

## 概要

nikkiプロジェクトにおける開発プロセス、ブランチ戦略、変更管理の統一ルールを定義する。

## 🚨 必須開発フロー

### 1. タスク開始前

```
1. タスクファイル読み込み (doc/task/{task}.md)
2. 要件定義書確認 (doc/requirement.md)
3. 技術ルール確認 (doc/rule/*)
4. ブランチ作成 (feature/{task-name})
```

### 2. 開発中

```
1. TDD実装 (テスト → 実装 → リファクタリング)
2. 技術ルール遵守チェック
3. 変更があれば即座にドキュメント更新
4. 定期的なコミット (機能単位)
```

### 3. タスク完了時

```
1. 完了条件チェック
2. 全テスト実行・合格確認
3. ドキュメント最終更新
4. Pull Request作成
5. レビュー・マージ
```

## ブランチ戦略

### ブランチ命名規則

```
main                           # 本番用メインブランチ
├── feature/task-01-llm-settings    # 機能開発ブランチ
├── feature/task-02-chat-interface  # 機能開発ブランチ
├── fix/task-01-settings-bug        # バグ修正ブランチ
└── docs/update-requirements        # ドキュメント更新ブランチ
```

### ブランチルール

- **1タスク = 1ブランチ = 1PR** (厳格遵守)
- ブランチ名: `{type}/task-{number}-{brief-description}`
- タイプ: `feature` / `fix` / `docs` / `test` / `refactor`
- mainブランチから直接作成
- 機能横断的な変更は禁止

## Pull Request (PR) 戦略

### PR作成ルール

```markdown
# PR Template

## 対応タスク

- [ ] `doc/task/{task}.md` の完了条件を全て満たしている

## 変更内容

- 機能追加: [具体的な機能]
- 技術的変更: [アーキテクチャ、ライブラリ等]
- テスト追加: [追加したテストの種類と範囲]

## テスト結果

- [ ] `npm run test:unit` - 単体テスト合格
- [ ] `npm run test:integration` - 結合テスト合格
- [ ] `npm run test:e2e` - E2Eテスト合格 (該当する場合)
- [ ] `npm run lint` - ESLint合格
- [ ] `npm run type-check` - TypeScript型チェック合格

## ドキュメント更新

- [ ] 要件定義書更新 (変更があった場合)
- [ ] タスクファイル更新 (完了条件変更があった場合)
- [ ] その他関連ドキュメント更新

## 動作確認

- [ ] 新機能が期待通りに動作することを確認
- [ ] 既存機能に影響がないことを確認
- [ ] ブラウザリロード後もデータが保持されることを確認

## 技術ルール遵守チェック

- [ ] アーキテクチャ層分離に準拠
- [ ] TypeScript strict mode準拠
- [ ] テストピラミッド構成準拠
- [ ] コーディング規約準拠
```

### PR承認条件

- [ ] 全テスト合格
- [ ] 技術ルール遵守
- [ ] ドキュメント整合性確認
- [ ] 動作確認完了

## 変更管理ルール

### 🚨 要件・仕様変更時の必須手順

#### 1. 即座に実行（作業中断してでも）

```
1. 変更内容をメモ・記録
2. 現在のブランチの作業状況を保存 (WIP commit)
3. ドキュメント更新作業に移行
```

#### 2. ドキュメント更新（優先度: 最高）

```
1. 要件定義書更新 (doc/requirement.md)
   - 変更箇所の明確化
   - 変更理由の記録
   - 影響範囲の特定

2. 該当タスクファイル更新 (doc/task/{task}.md)
   - 作業内容の修正
   - 完了条件の更新
   - 動作確認項目の調整

3. 関連タスクへの影響確認
   - 他のタスクファイルへの影響チェック
   - 依存関係の再確認
   - スケジュール影響の評価
```

#### 3. 技術的影響の評価

```
1. アーキテクチャへの影響確認
2. テスト戦略への影響確認
3. データモデルへの影響確認
4. 既存実装への影響確認
```

#### 4. 開発再開

```
1. 更新されたドキュメントに基づく作業計画再確認
2. 必要に応じてブランチ・実装の見直し
3. テストケースの見直し
4. 開発作業再開
```

## 開発環境・ツール設定

### 必須package.json スクリプト

```json
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start",
    "test:unit": "jest __tests__/lib __tests__/components",
    "test:integration": "jest __tests__/integration",
    "test:e2e": "playwright test",
    "test:watch": "jest --watch",
    "test:all": "npm run test:unit && npm run test:integration && npm run test:e2e",
    "lint": "next lint && eslint . --ext .ts,.tsx",
    "lint:fix": "next lint --fix && eslint . --ext .ts,.tsx --fix",
    "type-check": "tsc --noEmit",
    "format": "prettier --write .",
    "pre-commit": "npm run lint && npm run type-check && npm run test:unit"
  }
}
```

### Git Hooks設定

```bash
# .husky/pre-commit
npm run pre-commit
```

## 品質ゲート

### 各段階での必須チェック

#### コミット時

- [ ] ESLint エラーなし
- [ ] TypeScript型エラーなし
- [ ] 関連する単体テスト合格

#### PR作成時

- [ ] 全テスト合格
- [ ] タスク完了条件達成
- [ ] ドキュメント整合性確認

#### マージ時

- [ ] レビュー承認
- [ ] CI/CD パイプライン合格
- [ ] 本番環境デプロイ可能状態

### 技術的制約・制限事項

- プロトタイプ段階での制約を明確化
- 将来対応予定事項との区別
- 回避策・代替案の記録

## プロセス遵守の監視

### セルフチェックリスト（開発者）

- [ ] 1タスク1ブランチを遵守している
- [ ] 変更時にドキュメント更新している
- [ ] 技術ルールを遵守している
- [ ] テストを書いてから実装している

### 定期確認項目

- ドキュメントと実装の整合性
- 未対応の変更要求
- 技術的負債の蓄積状況
- テストカバレッジの維持

## 緊急時の対応

### 重大な仕様変更・方針転換時

1. **即座に全作業停止**
2. **現在の状況を完全に文書化**
3. **影響範囲の完全な洗い出し**
4. **新方針に基づくドキュメント全面更新**
5. **実装の見直し・作り直し判断**
6. **作業再開**

### 技術的問題・ブロッカー発生時

1. **問題の詳細記録**
2. **回避策・代替案の検討**
3. **関連ドキュメントへの制約事項追記**
4. **将来対応計画の策定**
